# xmatcher review audit — documentation, CLI, catalogue naming

Date: 2026-10-21
Scope: current `main` at 0.5.1 plus unreleased changes.

## Verdict

| Requirement | Verdict |
|---|---|
| Docs are current and do not describe removed code | **Pass after fixes.** Six concrete drift items were found and corrected; no broken relative links or missing documented imports remain. |
| CLI is usable and self-explanatory without the docs | **Mostly pass after fixes.** The `match` help had a formatting bug and could not express positional-error overrides, which made `skyerr` / `skyellipse` / probabilistic matching silently degrade. | Medium | `--endpoint` and `discover` omitted `cadc`, which the resolver supports. | Listed. |

| Low | `xmatcher list` reported 55 aliases but never showed them; `describe gaia` did not say it resolved an alias. | Added `list --aliases` and an `Alias:` line in `describe`. |

### Remaining CLI risks

- `xmatcher` with no arguments prints only the "at least two catalogues" error. It hints at `--help`, but a one-line usage synopsis would be friendlier.
- `match --help` is still roughly 250 lines. A "Start here" block was added and the side-override keys are listed once, but a two-tier `--help-all` would make the core path shorter.
- `--side1/--side2` cannot express `astrometric_covariance_columns` (a dict) or `columns`; those remain YAML/Python-only and are intentionally excluded.
- Input read failures other than output writes can still surface as "Unexpected error" with a traceback log entry. Only output errors were converted to `InputError` in this pass.
- `--priors` / `--probabilistic` still require the user to know that positional errors are a prerequisite; the help now says so, and `--fallback-policy error` makes the failure explicit.

## 3. Catalogue naming

### What already has a standard

- **VizieR**: `II/349/ps1`, `I/355/gaiadr3`, `J/A+A/682/A34/erass1-m`.
  These are stable catalogue/table ids and were already used correctly as
  `access_identifier` values. The only registry entry with a broken access id
  was `galex` (`II/335`, the catalogue parent), fixed to `II/335/galex_ais`.
- **TAP**: `schema.table` (`nsc_dr2.object`, `gaiadr3.gaia_source`). These are
  unambiguous only together with an endpoint.
- **HATS**: HATS is a storage format, not a naming authority. The IVOA HATS
  services register short names (`two_mass`, `gaia_dr3_stsci`) and LSDB's
  `data.lsdb.io` exposes provider-qualified copies (`des_dr2_us_east_s3`,
  `gaia_dr3_stsci`). The same survey therefore has several valid names, and
  some copies are `s3://` only, which xmatcher does not read. Treating a HATS
  short name as a universal survey id would be incorrect today.

### Proposed grammar (implemented)

`xmatcher` now accepts, in resolution order:

1. local file / HATS directory;
2. configured name or alias (case-insensitive);
3. `vizier:<id>` — exact VizieR table;
4. `tap:<endpoint>/<table>` — exact table on `vizier`, `noirlab`, `gaia`, or `cadc`;
5. `hats:<url>` — remote HATS over HTTP(S)/VOSpace.

Configured tables are matched first by `access_identifier`, so
`vizier:II/349/ps1` resolves to the curated `ps1` entry without a network probe.

Bare names follow `<survey>[_<release>][_<product>][_<provider>]`, lowercase
ASCII with `_` separators. Provider is only present when the same product lives
in multiple archives; `gaia` stays provider-neutral while `gaia_cds`,
`gaia_esa`, and `gaia_noirlab` are pins.

`hats:<name>` is deliberately rejected with guidance: the registry is not
stable enough to guess a URL. When LSDB/IVOA expose a durable short-name
resolution service, `hats:<name>` can be implemented without changing the
grammar.

There is a concrete interoperability gap behind that decision: LSDB's
`data.lsdb.io` tree currently exposes `partition_info.csv` and collection
roots, while `mirror.py` requires a single tree with
`partition_info.parquet`. Some LSDB/IRSA copies are `s3://` only, and xmatcher
has no S3 storage backend. Until the mirror accepts CSV partition tables and
collections (or a signed HTTPS mirror is used), `hats:<url>` is only usable for
trees that satisfy those requirements.

**Resolved 2026-10-22.** The mirror accepts CSV partition tables (including the
`Norder,Dir,Npix,count` shape with no `file_loc`) and pixel directories
(`Npix=N/part*.parquet`); collection roots — HTTPS and `s3://` — are descended
to their primary tree; and `xmatcher.s3` reads public buckets anonymously over
plain HTTPS, so the STScI/IRSA/MAST `s3://` registrations sync without
credentials. See [hats-sources.md](hats-sources.md).

### Current registry deviations

**Status: implemented later the same day.** The full migration table, including
every kept alias, is in [naming.md](naming.md). The renames were:

- `gaia_cds` → `gaia_dr3_cds`
- `des` → `des_dr2`; `nsc` → `nsc_dr2`; `ps1` → `ps1_dr1`
- `twomass` → `twomass_psc`; `unwise` → `unwise_dr1`
- `desils` → `legacy_dr10` (the Data Lab schema name is not a survey name)
- `decals_objects` → `decals_dr10_object` (the `decals` alias still points at
  `legacy_dr10`, so DECam photometry is not silently dropped)
- `gaia_noao` → `gaia_noirlab`; `ukidss` → `ukidss_las`

Every former key is still an alias, and a regression test
(`test_former_catalogue_keys_remain_valid_aliases`) now pins the old names to
their tables.

## Follow-up, 2026-10-22

Items 2–5 are closed; this section records what the fixes look like so the
audit is not re-read as a list of open work.

- **Live schema drift (2).** `tests/test_catalogue_live.py` (opt-in with
  `XMATCHER_LIVE=1`) checks every bundled `access_identifier` and every declared
  RA/Dec, error, motion and `default_columns` entry against the live
  `TAP_SCHEMA`, skipping only when an archive is down (Data Lab returned 502 for
  every endpoint during the run).
- **HATS policy (3).** `hats:<name>` now resolves through the IVOA registry with
  a seven-day cache; collection roots descend to their primary tree, skipping
  margin and index trees; HTTP walks ignore the absolute parent-directory row
  that made every LSDB tree look incomplete. `docs/hats-sources.md` lists the
  verified trees, and `xmatcher list --hats` prints the live inventory.
- **Help and usage (4).** A bare `xmatcher` prints
  `Usage: xmatcher CAT1 CAT2 …`; the long `match --help` keeps its "Start here"
  block.
- **Input errors (5).** `_guarded` reports `OSError` as `Error: …` without a
  traceback, and remote HATS in `match` names the `xmatcher sync` command
  instead of failing on a mangled path.
- **Not done:** the YAML schema reference and generated `docs/api.md` remain
  open; both are documentation work with no behavioural drift. `--help-all`
  was not added — the "Start here" block already covers the common path.
